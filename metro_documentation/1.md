
# 7. Don't confuse ticket type and ticket status

This is probably the source of some of the confusion in your current design.

They represent **two completely different things**.

### Type = What did the passenger buy?

```text
SINGLE
DAILY
MONTHLY
```

### Status = What is happening to the ticket?

```text
ACTIVE
USED
CANCELLED
```

So:

```text
Ticket
Type: SINGLE
Status: ACTIVE
```

means:

> Passenger purchased a single-trip ticket and hasn't used it yet.

Whereas:

```text
Ticket
Type: DAILY
Status: ACTIVE
```

means:

> Passenger purchased a daily pass and it is currently valid.

And:

```text
Ticket
Type: SINGLE
Status: USED
```

means:

> The passenger has already completed the trip.

# 8. The "ticket gets updated when loaded" idea

I think I understand what your lecturer was getting at.

Suppose the ticket is stored in a file.

Imagine:

```text
Ticket:
Type = DAILY
Status = ACTIVE
Purchase Date = 1 September
Valid Until = 1 September 23:59
```

Then the application is closed.

The next day, the application starts.

If you simply load the ticket from the file, it still says:

```text
ACTIVE
```

even though the ticket is no longer valid.

That's bad.

So your application needs to **recalculate/update ticket state when tickets are loaded**.

This is probably what your lecturer meant.

You can solve this elegantly.

When loaded:

```java

```

The ticket checks the current date/time.

Conceptually:

```java
if (status == CANCELLED)
    return;

    status = USED;
```

However, I would make one important change.

# 10. Expired isn't necessarily "USED"

This is a subtle but important real-world distinction.

Consider:

```text
Daily ticket
Bought at 8:00 AM
Valid until midnight
Passenger never used it
```

At midnight, should it become:

```text
USED
```

Not really.

It has **expired**, not been used.

So I'd actually recommend:

```java
ACTIVE
USED
CANCELLED
EXPIRED
```

If your lecturer only allows:

```text
ACTIVE
CANCELLED
USED
```

then you can keep those three and explain:

> A ticket becomes `USED` after it has been consumed/its validity period has ended.

But if you're allowed to extend the design, I'd strongly prefer:

```text
ACTIVE
USED
CANCELLED
EXPIRED
```

It makes the system much more realistic.

# 29. Don't make `updateTicket()` mean "randomly change the ticket"

Instead, I'd make the ticket lifecycle explicit.

```text
                 purchase
                    ↓
                 ACTIVE
                /      \
          cancel        use
             ↓           ↓
        CANCELLED       USED
             
ACTIVE
   │
   │ validity ends
   ↓
EXPIRED
```

And importantly:

```text
CANCELLED → cannot become ACTIVE
USED      → cannot become ACTIVE
EXPIRED   → cannot become ACTIVE
```

That's a proper state machine.

# 30. A particularly nice Java design

You can represent the states using enums:

```java
public enum TicketStatus {
    ACTIVE,
    USED,
    CANCELLED,
    EXPIRED
}
```

and:

```java
public enum TicketType {
    SINGLE,
    DAILY,
    MONTHLY
}
```

Then your ticket could conceptually be:

```java
public class Ticket {

    private String id;
    private Passenger passenger;

    private Station sourceStation;
    private Station destinationStation;

    private double fare;

    private TicketType type;
    private TicketStatus status;

    private LocalDateTime purchaseDateTime;
    private LocalDateTime validFrom;
    private LocalDateTime validUntil;
}
```

Using `LocalDateTime` is much better than storing date and time as arbitrary strings.

# 34. The full scenario you can present to your lecturer

You can describe your application like this:

> **The Metro Management System consists of two primary actors: passengers and administrators. Administrators configure and maintain the metro network by managing stations, routes, and trains. Passengers use the configured network to search for journeys and purchase tickets.**
> 
> **An administrator first creates stations with their names and locations. Routes can then be created between stations with a specified distance. Trains are registered with their capacity and can be assigned to available routes. This information forms the metro network used by passengers.**
> 
> **A passenger registers or logs into the system and maintains a balance. The passenger selects a source station, destination station, and ticket type. The system verifies that a valid route exists and calculates the fare based on the route distance and ticket type. If the passenger has sufficient balance, the fare is deducted and a ticket is created.**
> 
> **Each ticket contains the passenger, source station, destination station, fare, ticket type, status, purchase date/time, and validity period. Single tickets are intended for one journey, while daily and monthly tickets can be used repeatedly during their validity period.**
> 
> **Tickets have a lifecycle. A newly purchased ticket is active. A single ticket becomes used after the journey is completed. A passenger may cancel an unused ticket according to the system's cancellation policy. Tickets whose validity period has ended become expired. When the application starts, tickets are loaded from persistent storage and their statuses are updated according to the current date and time. This ensures that the ticket status remains correct even when the application was previously closed.**
> 
> **The file manager is responsible only for persistence and does not contain metro business logic. The various management classes handle the corresponding business operations, while the Metro System coordinates the components.**

That is a **complete scenario**, rather than just a collection of classes.

## The central principle

The most important thing is to make **every class participate in a believable business process**.

Don't design it as:

```text
Station = CRUD
Train = CRUD
Route = CRUD
Ticket = CRUD
```

Design it as:

```text
ADMIN
  ↓
builds metro network
  ↓
STATIONS + ROUTES + TRAINS
  ↓
PASSENGER
  ↓
chooses journey
  ↓
ROUTE
  ↓
distance
  ↓
FARE
  ↓
TICKET
  ↓
ACTIVE
  ↓
VALIDATED
  ↓
USED / EXPIRED / CANCELLED
```

Once you structure it this way, **the relationships between your classes become obvious**, and your Java implementation becomes much easier to reason about.

If this is for an OOP/software-engineering assignment, I'd also recommend that your next step be to turn this into a **proper UML class diagram + use-case diagram + sequence diagrams + Java class responsibility breakdown**. That would give you a direct blueprint for implementing the project rather than having to invent the architecture while coding.
